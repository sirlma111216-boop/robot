# 고철왕: 스크랩 시티 챔피언십 — Claude Code 개발 프롬프트

이 문서 전체를 Claude Code에 전달한다. 별첨 이미지·오디오 제작 명세도 함께 읽는다. 사용자는 외부에서 이미지와 음악을 제작해 공급한다. 여기서 요구하는 작업은 게임의 실제 구현이며, 기획서·정적 목업·로컬 가짜 멀티플레이만 만들고 끝내지 않는다.

## 1. 너의 역할과 완성 목표

너는 온라인 게임 프로듀서, 프런트엔드/서버 개발자, 물리 시뮬레이션 개발자, 인터랙션 디자이너 역할을 수행한다. 한국 중학생이 설명을 오래 읽지 않고 시작할 수 있지만, 성인도 조합과 심리전을 즐길 수 있는 웹 게임을 구현하라.

게임명은 「고철왕: 스크랩 시티 챔피언십」이다. 고철 부품으로 로봇을 조립하고, 짧은 명령을 미리 입력한 뒤, 모든 로봇이 동시에 움직이며 충돌하는 대회다. 게임성 > 조작 이해도와 시각적 완성도 > 안정성 있는 학급 운영 > 과학 학습 콘텐츠 순으로 제품을 설계하되, 안정성과 보안은 출시 필수 조건이다.

기존 게임의 추상적 재미를 참고한다: Galaxy Trucker의 제한 시간 조립과 자기 기계에 대한 애착, Robo Rally의 미리 정한 명령이 상대와 충돌하며 어긋나는 재미. 원작의 카드 문구, 그림, 캐릭터, 로고, 보드 배치를 복제하지 않는다. 독자적인 부품·경기장·점수 규칙을 구현한다.

GitHub 저장소에 올릴 수 있는 소스, 실제 Cloudflare 배포 구성, 실행 가능한 테스트, 운영 문서까지 완성한다. 계정·자격증명·외부 제작 에셋이 없는 부분은 정확히 구분하고, 준비할 수 있는 코드와 검증을 모두 마친 뒤 외부 설정만 남긴다. 자격증명 없이 배포했다고 주장하거나, 임시 그래픽을 최종 미술이라고 주장하지 않는다.

## 2. 규모와 멀티플레이 모델

### 확정 기본값

- 한 클래스: 학생 계정 최대 30명, 교사 계정 1명. 교사는 학생 정원과 별개다.
- 기본 방 구성: 6개 방 × 학생 5명. 방당 활성 로봇 최대 6대. 학생·참가 중인 교사·봇을 모두 합친다.
- 따라서 학생 30명과 교사가 동시에 플레이해도 6개 방에 수용 가능하다. 교사가 들어갈 여섯 번째 자리를 봇이 차지한 경우 그 봇을 다음 안전한 단계에서 교체한다.
- 교사가 5개 방 × 6명으로 구성했다면 빈 자리가 없는 방에는 참가할 수 없다. 관전하거나, 경기 사이에 여섯 번째 방을 만들고 인원을 재배치한다. 사람을 임의로 퇴장시키지 않는다.
- 방 설정은 2~6대 경기 지원. 1명만 있는 경우 혼자 연습하거나 봇을 추가한다. 기본 추천은 4~6대다.
- 클래스에 속한 사람은 방을 관전할 수 있다. 관전자는 로봇 자리를 차지하지 않는다. 한 사용자는 한 시점에 한 경기 영상만 구독한다. 교사의 전체 현황은 모든 경기 영상을 동시에 렌더링하지 않고 요약 상태와 저빈도 썸네일로 제공한다.
- 학생 30명이라는 제한은 이 제품의 기본 운영 범위다. Cloudflare가 30연결까지만 허용한다는 의미가 아니다. 30인 단일 경기, 8인 이상 방, 여러 학급 동시 운영은 후속 성능 검증 전까지 지원을 표방하지 않는다.

### 실시간의 정의

참가자들은 같은 방에서 동시에 조립하고 명령을 제출하며, 같은 시각에 같은 전투를 본다. 전투 중 방향키로 계속 조종하는 액션 게임은 아니다. 기본 모드는 “동시 명령 계획 + 권위 있는 서버 물리 계산 + 동기화된 연속 전투 재생”이다. 이 선택을 처음 화면에서 짧은 움직이는 예시로 알려라.

경기당 6대는 물리 계산 한계라는 단정이 아니라, 로봇 식별성·충돌 가독성·짧은 대기시간을 위한 설계 상한이다. 실제 안정적인 수용 인원은 배포 환경에서 측정해 발표한다.

## 3. 세계관, 스토리와 서로 다른 화면

폐공장 도시 스크랩 시티에서 신입 정비사가 고철 로봇 대회에 참가한다. 안내 정비사 미라, 방송 드론 볼트, 라이벌 팀장 렉스가 등장한다. 대사는 장면당 1~2줄, 3초 이내 읽을 분량이며 건너뛰기 가능하다. 과학 수업이나 교실을 시각적 테마로 사용하지 않는다.

한 화면의 제목과 본문만 갈아 끼우는 구조를 금지한다. 다음은 구도·배경·입력 방식이 실제로 다른 Scene 또는 Route다.

| 화면 | 구도와 행동 | 핵심 버튼/다음 행동 |
|---|---|---|
| 도시 입구 | 도시의 야경, 간판과 움직이는 크레인, 큰 선택 카드 | 혼자 연습 / 클래스 입장 / 교사 |
| 클래스 격납고 | 학생 로봇의 작은 아바타, 방별 격납고 문, 방장 배지 | 내 방 입장 / 빈 방 참여 |
| 고철 경매장 | 컨베이어 위 실물 크기의 부품, 집게와 선택 영역 | 부품 선택 |
| 개인 정비소 | 큰 로봇 조립대, 장착 위치, 즉시 움직여보는 시험장 | 장착 / 시험 운전 / 준비 완료 |
| 경기장 진입 터널 | 로봇 소개, 각자의 실루엣과 고유 색·문양 | 준비 확인 또는 짧은 자동 전환 |
| 전술 준비실 | 실제 경기장 미리보기와 명령 슬롯 3개 | 순서 정하기 / 명령 확정 |
| 경기장 중계 | 전투가 화면 대부분을 차지하고, 점수·명령 진행만 노출 | 관전 시 대상 전환 / 소리 |
| 피트스톱 | 손상 표현을 정리하고, 무료 교체 또는 다음 빌드 선택 | 하나 교체 / 다음 경기 |
| 시상대 | 실제 조립 로봇, 짧은 하이라이트, 점수 근거 | 재대결 / 격납고로 |
| 교사 관제실 | 클래스 명단, 방 현황, 제어 버튼, 선택 방 관전 | 방장 지정 / 봇 / 관전 / 참가 |

첫 챕터는 폐차장 예선, 둘째는 강철 주조장, 셋째는 네온 도크 결승이다. 세 경기장은 배경만 바꾸지 않고 장애물 배치와 지형 효과를 바꾼다. 물리 콜라이더와 게임 오브젝트는 배경 이미지와 분리한다.

최초 연습은 “부품 하나 장착 → 전진 카드 넣기 → 범퍼 가동 → 봇 밀어보기”의 60~90초 상호작용으로 구성한다. 설명 팝업 여러 장을 읽게 하지 않는다.

## 4. 첫 출시의 구체적인 경기 규칙

### 세션 흐름

기본 3경기 대회, 한 경기 6턴. 예상 전체 길이 15~20분을 목표로 실제 측정한다. 교사는 빠른 1경기 또는 표준 3경기를 선택할 수 있다. 기본 시간은 부품 선택 60초, 조립 75초, 턴 계획 20초, 전투 9초, 결과 정리 3초, 경기 사이 피트스톱 30초다. 시간은 설정 데이터로 둔다. 전원 준비 완료 시 교사 설정에 따라 일찍 진행한다.

### 부품 선택과 조립

온라인 접속 지연이 좋은 부품 획득을 결정하지 않도록 공용 부품을 “가장 먼저 클릭한 사람”에게 주지 않는다. 모두 우선순위 두 개를 동시에 고르는 짧은 선택 단계를 사용한다. 경쟁 부품은 라운드마다 순환하는 공개 우선권으로 배분하고, 놓친 사람에게 다음 선택 우선권을 준다. 동일한 예산의 기본 키트는 항상 제공한다. 느린 참가자를 위해 자동 조립 프리셋 3종을 제공한다.

부품은 처음부터 모두 구입 가능하게 만들지 말고 한 대회 내 드래프트에서 고른 구성으로 차별화한다. 장기 플레이 보상은 외형만 바꾼다. 학생 경험치에 따른 능력 격차, 유료 능력, 출석 보상은 넣지 않는다.

로봇은 섀시 1개, 주행 장치 1쌍, 전면 장치 1개, 보조 장치 최대 2개로 제한한다. 자유 그리드처럼 보이더라도 실제 첫 버전은 명확한 하드포인트 장착 방식으로 만든다. 카드별 효과와 장착 방향을 시각적으로 표시한다.

- 섀시: 경량 / 표준 / 중량. 질량·회전 관성·에너지 한도에서 차별화.
- 주행: 일반 바퀴 / 광폭 타이어 / 무한궤도. 마찰과 선회 성질에서 차별화.
- 전면: 용수철 범퍼 / 쐐기 플라우 / 전자석.
- 보조: 고정 브레이크 / 단발 부스터 / 안정화 장치 / 보강판 중 최대 2개.
- 유효 조합에는 공통 질량 예산과 에너지 예산이 있다. 모든 장점을 동시에 가져갈 수 없다.

전자석은 자성 반응이 설정된 물체에만 작동한다. 모든 금속이 자석에 붙는다는 규칙을 만들지 않는다. 자석 힘에는 거리 감쇠와 힘 상한이 있고 상대에게 가한 힘의 반작용이 자신의 몸에도 작용한다. 고정 브레이크는 무조건 위치 고정이 아니라 접지 저항을 높인다.

### 명령과 전투

매 턴 3개 슬롯에 명령을 배치한다. 카드풀은 전진 / 후진 / 좌회전 / 우회전 / 제동 / 전면 장치 작동 / 보조 장치 작동 / 대기로 시작한다. 전진은 슬롯 동안 엔진 힘을 가하고, 회전은 목표 각도에 접근하도록 토크를 가한다. 위치 순간이동이나 정확한 칸 단위 보간으로 물리를 대체하지 않는다.

각 슬롯 3초, 총 9초 동안 로봇들이 동시에 작동한다. 결과는 상대 위치·무게·마찰·벽·기계 반동에 따라 달라진다. 명령마다 에너지 비용이 있으며 에너지는 턴 단위로 회복된다. 불가능한 명령은 제출 전에 표시하고 서버에서 다시 검증한다.

계획 미리보기는 “다른 로봇과 부딪히지 않을 경우”의 자신의 예상 경로만 점선으로 보여준다. 상대의 아직 공개되지 않은 명령, 정확한 결과를 보여주지 않는다. 전투 전 고정된 명령은 잠금 아이콘으로 표시하고, 재생 중인 슬롯은 화면 아래에서 자연스럽게 강조한다.

전투 구간 사이에는 공개된 정비 드론이 모든 로봇의 움직임을 안정화하는 짧은 연출을 넣을 수 있다. 사용할 경우 서버 규칙에도 명시하고 전체 로봇에 똑같이 적용한다. 보이지 않는 속도 초기화로 관성이 사라지게 하지 않는다.

### 승패와 역전

6턴 누적 점수로 한 경기 승패를 정한다. 초기 값은:
- 전투 종료 시 중앙 왕관 영역을 단독 점유: 3점. 둘 이상 점유하면 0점.
- 상대를 낙하 구역으로 밀어낸 명확한 기여: 2점. 마지막 유효 충격과 시간 창을 서버 이벤트로 판정하며 스스로 떨어진 경우 공격자 점수를 주지 않는다.
- 지도에 제한 수량 생성되는 고철 캡슐: 1점. 생성 순서와 수량은 공개 규칙이다.
- 동점이면 왕관 점수, 그다음 낙하 기여, 그다음 공동 순위로 처리한다. 추가로 길어지는 무한 연장전은 없다.

낙하하면 그 턴만 정비 구역에서 쉬고 다음 턴 안전한 시작점에 복귀한다. 영구 탈락이 없고, 첫 버전에는 부품 영구 파괴를 넣지 않는다. 손상 표현은 시각 효과와 짧은 일시 상태로 처리한다. 출발 지점 봉쇄·반복 낙하·왕관 독점 방지 규칙을 테스트한다.

경기 사이에는 모든 참가자가 같은 가치의 교체 선택을 받는다. 열세 참가자에게 부품 선택 우선권을 줄 수 있지만 몰래 능력치를 올리는 보정은 하지 않는다. 최종 우승은 세 경기 순위 포인트 합산으로 정한다. 구체 점수표는 인원별 데이터로 관리하고 화면에 보여준다.

이 규칙은 초깃값이다. 봇 경기와 사람 테스트에서 지배적 조합이 나오면 근거를 기록하고 조정한다. 게임의 핵심인 조립·명령·충돌·개조를 삭제하여 일정만 맞추지 않는다.

## 5. 학생·방장·교사·봇 권한

교사가 클래스를 만들면 만료되는 입장 코드를 얻는다. 학생은 코드와 닉네임으로 입장한다. 학생 명단에서 교사가 방장을 지정하면 해당 학생의 방이 만들어지고 그 학생의 플레이어 자리도 자동으로 확보된다. 별도의 “게임 참여” 버튼을 다시 누르게 하지 않는다. 다른 학생은 빈자리가 있는 방을 직접 선택하거나 교사가 자동 분배한다.

| 행위 | 학생 | 방장 | 교사 |
|---|---|---|---|
| 자기 로봇·명령 설정 | 가능 | 가능 | 참가 중이면 가능 |
| 방 준비 상태 확인 | 가능 | 가능 | 가능 |
| 방 시작·재대결 | 불가 | 교사가 연 범위에서 가능 | 가능 |
| 방장 지정·교체 | 불가 | 불가 | 가능 |
| 클래스 배정·강퇴·잠금 | 불가 | 불가 | 가능 |
| 봇 추가·제거·난도 변경 | 불가 | 기본 불가 | 가능 |
| 다른 방 관전 | 설정에 따라 | 설정에 따라 | 가능 |
| 게임 규칙 수정 | 불가 | 불가 | 경기 시작 전만 가능 |

교사는 기본 관전자다. 참가 버튼을 누르면 빈 슬롯을 차지하며 일반 플레이어와 동일한 정보만 받는다. 운영 권한은 유지하지만 상대의 비공개 명령을 볼 수 없다. 교사가 자신이 참가한 경기에 개입해 봇이나 규칙을 바꾸려 하면 변경 사실을 모두에게 보여주고 안전한 다음 단계에 적용한다. 필요하면 해당 경기를 연습 모드로 표시한다.

경기 도중 입장한 학생·교사는 먼저 관전하고 다음 턴 또는 다음 경기 중 규칙상 안전한 지점에 참가한다. 실행 중인 로봇을 즉시 교체하지 않는다. 방 변경은 기존 자리를 먼저 안전하게 반납하고 한 사용자에게 활성 자리가 중복되지 않게 한다.

방장이 끊겨도 서버가 경기를 계속 진행한다. 60초 재접속 유예 후 교사가 새 방장을 지정할 수 있다. 교사가 접속하지 않은 경우 사전에 공개한 순서로 방의 사람 참가자 중 임시 방장을 선정하고 알린다. 사람 전원이 떠나면 유한한 정리 절차 후 방을 종료한다.

### 봇 모드

1. 혼자 연습: 사용자 1명 + 봇 1~5대. 로그인과 클래스 없이 가능. 동일한 게임 코어를 Web Worker에서 실행하는 LocalTransport를 사용한다.
2. 교사의 방별 봇 추가: 빈 슬롯에 투입. 사람+봇 합계 6대 제한. 방마다 난이도와 플레이 성향을 설정.
3. 교사의 자동 시뮬레이션: 비어 있는 시험 방에 봇 2~6대를 넣어 한 경기 또는 대회를 실행하고 관전. 학생 방장이 필요한 일반 방과 별도로 “시험 방 / 시스템 운영”으로 표시한다.
4. 참가자 연결 끊김: 유예 동안 마지막 제출 명령 또는 안전한 기본 명령. 이후 임시 봇이 기존 자리와 로봇을 이어받는다. 재접속하면 다음 계획 단계에 통제권 반환.

봇은 외부 LLM API를 호출하지 않는다. 공개된 상태에서 후보 명령 조합을 제한 수만 평가하는 휴리스틱으로 만든다. 쉬움은 제한된 탐색과 실수 확률, 보통은 거점·안전·밀기 판단, 어려움은 짧은 예측 탐색을 사용한다. 숨겨진 상대 명령을 읽거나 물리 규칙을 무시하지 않는다. 봇 계산 예산에 상한을 두고 난도별 CPU 비용을 측정한다. 운영 중 경기 1배속, 2·4배속과 일시정지는 봇 전용 시험/솔로에서만 허용한다. 반복 시험은 기본 1대회, 최대 횟수와 총 실행시간을 반드시 둔다.

## 6. 초보자 UX와 화면 품질

- 기본 한국어, 첫 화면부터 게임의 목적을 “로봇을 만들고, 세 수를 읽어라”처럼 짧게 제시.
- 학생 화면에는 한 번에 하나의 주 행동을 강조. 제목·한 줄 안내·실행 버튼으로 기본 흐름을 이해 가능하게 한다.
- 부품 선택은 그림 우선. 기본 표시는 무게·밀기·접지 같은 최대 3개 아이콘 지표. 세부 수치는 펼치기에서만.
- 명령 카드는 긴 문장 대신 방향·범퍼·브레이크 아이콘과 한 단어 라벨. 장치가 없으면 장치 카드가 비활성화되는 이유를 해당 부품 위치에서 짧게 알려준다.
- “준비됐어요 / 친구 기다리는 중 / 지금 움직여요”를 구분하고 타이머, 준비 인원, 내 로봇을 항상 식별 가능하게 한다.
- 대기 중에는 내 로봇 작은 시험 운전이나 부품 미리보기 제공. 비공개 전투 결과를 먼저 보여주지 않는다.
- 드래그 외에 클릭→슬롯 선택 방식 지원. 키보드 이동·확정도 지원. 44px 이상 터치 대상, 명확한 포커스.
- 색만으로 플레이어를 구분하지 말고 번호·문양·외곽선 병행. 내 로봇 추적 링, 방향 표시, 화면 밖 포인터 제공.
- 기본 1366×768 노트북과 1024×768 태블릿 가로에서 검증. 16:9 경기장을 비율 유지로 맞추고 좁은 화면은 HUD 재배치. 세로폰은 가로 전환 안내와 로비·관전 지원을 우선한다.
- 전투 점수 텍스트가 로봇을 덮지 않도록 제한. 6대 모두 읽히는 카메라 범위 유지. 전체 지도를 못 보는 극적인 확대는 하이라이트 재생에서만 사용한다.
- 짧은 화면 흔들림, 충돌 섬광, 바퀴 먼지, 금속 소리로 타격감을 준다. 강한 흔들림·섬광·잔상은 사용자 설정으로 줄인다.
- 이모지, CSS로 그린 임시 로봇, 도형으로 그린 인물을 최종 디자인으로 사용하지 않는다. UI의 패널·게이지·글자·벡터 방향선은 코드로 정확히 그려도 된다.
- 교사의 정보 밀도는 높일 수 있으나 학생 화면을 운영 대시보드처럼 만들지 않는다.

## 7. 렌더링·물리·동기화

### 기본 기술 선택

TypeScript 모노레포, React + Vite로 로비와 UI, Phaser로 2D 경기 렌더링, standalone Matter.js를 감싼 순수 TypeScript 헤드리스 시뮬레이션을 기본안으로 한다. 개발 시점의 호환되는 안정 버전을 확인하고 lockfile에 고정한다. Phaser 내장 Matter 포크와 npm Matter.js가 자동으로 같은 버전이라고 가정하지 않는다.

서버의 물리 엔진만 승패를 결정한다. 클라이언트 Phaser는 서버 궤적을 렌더링하고 부가 연출을 한다. 별도의 클라이언트 물리 엔진이 결과를 재결정하지 않는다. 엔진을 바꿀 수 있는 PhysicsAdapter 경계를 둔다.

### 물리 규격

- 2D 탑다운, 중력 0. 기본 고정 시간 간격 1/60초. 빠른 물체는 속도 상한, 서브스텝 또는 스윕 판정으로 관통 방지.
- 섀시는 하나의 안정적인 복합 강체로 구성하고 장착 부품으로 질량·관성·충돌 형상을 계산한다. 장식 부품마다 독립 조인트를 만들지 않는다. 움직이는 실제 강체는 로봇 포함 방당 12개, 복합 콜라이더 구성은 로봇당 8개 이하를 초깃값으로 한다.
- 엔진 힘, 선회 토크, 제동, 충격량, 반발, 감쇠를 명시적으로 조절한다. 자석은 힘, 범퍼는 축적 후 방출되는 충격량과 반동으로 계산한다.
- 탑다운에서 Matter의 물체 접촉 friction만 조절한다고 타이어와 바닥의 마찰이 구현되는 것은 아니다. 바닥 재질별 종방향 구동력 한도, 횡방향 미끄럼 감쇠, 제동 저항을 별도의 접지 모델로 구현한다.
- 무게가 큰 로봇은 같은 힘으로 덜 가속되고 회전 응답도 달라야 한다. 고정 장치는 무한 질량이 아니다. 과도한 자석 인력은 클램프한다.
- 게임 수치를 실제 단위로 표시하려면 좌표·시간·질량 변환 계층을 검증한다. 검증하지 않은 경우 무게/출력 상대 지표를 사용하고 정확한 SI 실험 시뮬레이터라고 주장하지 않는다.
- 낙하·접지·자석 사거리·왕관 점유는 별도 센서와 규칙으로 판정. 이미지는 판정 경계를 정의하지 않는다.
- 충돌 eventId와 impulse 강도로 효과음을 고른다. 접촉 유지 프레임마다 충돌음을 반복하지 않는다.
- 시각적인 눌림·반동·휠 회전·잔상은 표현 계층이다. 충돌 판정과 위치를 임의로 바꾸지 않는다. 히트스톱은 전체 물리 시계를 멈추지 않는 국소 시각 효과로 구현한다.
- 시험장에 질량 차 밀기, 고마찰/저마찰 정지거리, 회전, 범퍼 반동, 자석 반작용, 얇은 벽 충돌 시나리오를 제공한다.

### 명령 단위의 서버 계산과 재생

1. RoomDO가 계획 마감 시각까지 명령을 받는다. 참가자·턴·소유권·에너지·명령 버전 검증.
2. 마감되면 명령을 고정하고 roundId, turnId, rulesVersion, seed, initialState를 영속 기록한다.
3. 제한된 물체와 고정 timestep으로 9초 구간을 빠르게 계산한다. 서버에 실제 9초 동안 돌아가는 60Hz 상시 루프를 기본안으로 만들지 않는다.
4. 최종 권위 상태, 시간표가 있는 이동 keyframe, 충돌·점수 이벤트를 기록한다. 최소 15~20Hz 궤적과 충돌 직전/직후 프레임으로 고속 충돌 궤적을 보존한다. 클라이언트에서 위치·회전 보간으로 60fps 렌더링한다.
5. 충분한 버퍼를 둔 startAt을 정하고 모든 클라이언트에 동일한 궤적을 전송한다. 시계 차이는 왕복시간 샘플로 보정하며 정확도가 부족하면 다음 구간에서 재동기화한다.
6. 모든 명령 제출 직후 늦어도 목표 지연 내 재생을 시작한다. 서버 계산 결과가 빨리 나왔더라도 사용자에게 다음 턴 결과를 미리 노출하지 않는다. UI와 후속 명령 수락은 실제 재생 종료 시점 이후다.
7. 재접속은 현재 phaseVersion과 재생 기준 시각으로 해당 지점부터 복귀한다. 결과 중복 적용을 막는다.

사전 계산은 서버의 최종 정답을 한 번만 만드는 구조다. 동일한 seed만 있으면 모든 브라우저에서 부동소수점 물리가 완전히 같다고 가정하지 않는다. 리플레이는 서버 궤적을 저장해 재생한다. 명령 및 seed는 감사·테스트·동일 엔진 버전 재계산용으로 보존한다.

한 방 6대/이동 강체 12개에서 9초 구간 계산 p95 250ms 이하를 목표로 프로파일링한다. 이는 보장값이 아니다. 충족하지 못하면 콜라이더·봇 탐색·동적 물체 수를 줄이고 측정한다. 실패 시 영구 60Hz 서버 루프로 몰래 전환하지 않는다. 사전 계산 청크화가 필요하면 실행 ID·체크포인트·마감 처리를 설계하고, 지속 계산이 필수인 모드로 확장할 때 별도 시뮬레이션 서비스 어댑터를 검토한다.

초기 트래픽 추산은 12개 물체 × 20샘플/초 × 9초 × 샘플당 약 32바이트 = 약 69KB/구간이다. 이벤트·압축·헤더에 따라 달라진다. 30개 수신 단말에 같은 규모를 보내면 약 2.1MB/전투 구간 수준이며 실제 사용량과 다르다. 이를 측정용 기준으로만 사용한다. 1메시지 크기, 느린 수신자 버퍼, 전체 구간 크기에 상한을 두고 청크별 checksum·번호를 사용한다. 대형 JSON 전체 상태를 프레임마다 전송하지 않는다.

## 8. Cloudflare와 GitHub 구조

- Cloudflare Workers + Static Assets를 프런트엔드/HTTP API 배포의 기본안으로 사용한다.
- 클래스마다 ClassSessionDO 1개: 참가자, 역할, 방 배정, 입장 코드, 요약 상태.
- 방마다 GameRoomDO 1개: 경기 권위 상태, 명령, 서버 물리 결과, WebSocket, 재접속.
- 위 두 개는 DO 클래스 정의이며 방이 6개라고 DO 클래스 정의를 6개 만드는 것이 아니다. 인스턴스를 나눈다.
- SQLite-backed Durable Objects를 사용한다. 경기 기록의 최근 구간과 체크포인트는 DO 저장소, 큰 장기 리플레이 및 미디어는 필요 시 R2. 초기 요구에 불필요한 D1/KV/Redis를 추가하지 않는다.
- Hibernation WebSocket API를 사용하고, 대기 중 상시 setInterval이나 빠른 ping으로 DO를 계속 깨우지 않는다. 유한한 단계 마감은 저장된 deadline과 alarm으로 관리한다. 알람 지연은 가능하므로 초 단위 방송처럼 신뢰하지 않는다.
- 단계 변경은 phaseVersion, matchId, commandId로 중복 방지. alarm 재시도, 오래된 명령, 동시에 준비 완료한 여러 클라이언트에도 한 번만 진행한다.
- 클래스와 방의 상태는 분산된 저장소이므로 서로 다른 DO 사이가 단일 트랜잭션이라고 가정하지 않는다. ClassDO를 자리 배정의 권위자로 삼고 예약→방 확인→확정 프로토콜, 예약 만료, idempotent RPC와 복구를 구현한다. 재접속·방 이동 중 두 방 동시 참여 또는 초과 정원이 생기면 안 된다.
- 매 물리 프레임 SQLite 쓰기를 하지 않는다. 명령 확정·계산 완료·단계 변경처럼 의미 있는 시점에 기록한다. 재생 자료를 먼저 영속화하고 완료 마커를 기록하여 장애 시 부분 결과를 최종 결과로 오인하지 않는다.
- DO가 휴면/재시작되면 저장된 상태와 WebSocket attachment로 복구한다. Map에만 있는 상태로 운영하지 않는다. 경기 계산 도중 장애 시 같은 실행 ID로 재개 또는 재계산해 단 한 번 결과를 확정한다.
- 공개 웹 배포는 HTTPS/WSS. Vite 개발 서버를 배포 서버로 사용하지 않는다. 브라우저만 연결한 BroadcastChannel/메모리 서버를 실제 멀티플레이 대체물로 제출하지 않는다.
- GitHub 자동 배포는 Workers Builds 또는 GitHub Actions 중 하나를 주 경로로 선택하고 중복 배포를 방지한다. wrangler 설정, DO migration, staging/production 별도 namespace, 정적 경로와 /api 및 /ws 라우팅을 제공한다.
- production 비밀값은 Workers Secrets/적절한 CI secret에 저장. 빌드 산출물, git, 브라우저에 교사용 비밀키를 넣지 않는다. 필요한 자격증명과 수동 계정 설정은 README에 명확히 안내한다.
- 리소스 생성 또는 비용이 발생하는 유료 기능 변경은 임의로 진행하지 않는다. 기존에 허가된 배포 환경 범위에서 실행한다. 인증정보가 없으면 로컬 검증과 배포 설정을 끝내고 실제 배포 미수행을 보고한다.
- SQLite DO는 무료 플랜에서도 제공되지만, 쿼터와 사용량으로 수업 중 차단되지 않는지 확인한다. 무료 운영 또는 비용을 보장하지 않는다. 실측 사용량과 현재 공식 단가로 학급 1회 이용 비용을 추정한다.

### 인증과 정보 보호

교사 생성/로그인은 서버 비밀값 기반의 초기 관리자 인증 또는 Cloudflare Access로 보호한다. 학생에게 배포되는 입장 코드는 교사 권한을 부여하지 않는다. 기본 구현은 관리자가 환경변수로 설정한 강한 교사용 접근 암호를 서버에서 검증해 짧은 교사 세션을 발급하는 방식으로 시작할 수 있다. 요청 제한과 실패 지연, 로그 비노출을 적용하고 향후 학교별 인증 어댑터로 교체 가능하게 한다.

교사 세션은 Secure, HttpOnly, 적절한 SameSite 쿠키를 사용하고 상태 변경 요청의 Origin/CSRF를 검증한다. 학생 세션도 재접속 가능한 서버 발급 자격으로 식별한다. 닉네임 자체를 신원키로 쓰지 않는다. WebSocket 업그레이드 때 세션·Origin·클래스/방 소속을 검증하고, 교사/방장 권한은 매 제어 명령에서 재검증한다. 메시지 schema, 크기 제한, 명령 빈도 제한을 둔다. 상대 명령·학생 전체 세션 토큰·교사 키는 다른 클라이언트에 보내지 않는다.

학생은 닉네임만 받으며 이메일·생년월일·실명은 요구하지 않는다. 닉네임 길이 제한·중복 처리·출력 이스케이프를 적용한다. 클래스 코드는 유효기간과 추측 방지 제한을 둔다. 기본 보존기간은 세션 종료 후 24시간으로 설정 가능하게 하고 교사 삭제 기능을 제공한다. 자유 채팅은 첫 버전에 넣지 않고 사전 정의된 이모트만 사용한다.

## 9. 확장·전면 개정에 견디는 구조

다음 책임을 나누되 작은 파일을 위한 과도한 서비스 분리는 하지 않는다.

```text
apps/web/                 React 화면, Phaser renderer, 접근성 UI
apps/worker/              HTTP/auth, ClassSessionDO, GameRoomDO
packages/game-core/       상태기계, 순수 규칙, 점수, 명령 검증
packages/physics/         PhysicsAdapter, Matter 구현, 궤적 기록
packages/protocol/        메시지 schema, 버전, 에러 코드
packages/bots/            공개 관측 기반 의사결정과 예산 제한
packages/content/         부품·경기장·챕터·봇 preset·균형 데이터
packages/assets/          manifest schema, ID 및 파생 에셋 매핑
tests/                    게임 규칙, 역할/네트워크, UI, 부하
docs/                     운영, 배포, 아키텍처, 에셋, 테스트 결과
public/assets/            공급된 최적화 이미지와 오디오
```

화면에서 승패 규칙을 결정하지 않는다. content의 부품 정의와 visualId, physicsSpec, abilityId를 연결한다. 활성 게임을 시작할 때 rulesVersion/contentVersion/physicsVersion을 고정한다. 업데이트 도중 진행 중인 게임에 새 수치를 섞지 않는다. 프로토콜 불일치 시 설명 후 안전한 재접속/업데이트를 요구한다.

NetworkTransport와 LocalTransport는 동일한 명령/이벤트 계약을 사용한다. 리플레이는 경기 코어와 분리하고 저장된 버전을 읽는다. 봇은 렌더러나 UI에 의존하지 않는다. 장래 팀전·새 장치·새 챕터·다른 물리 엔진이 기존 화면 전체 재작성으로 이어지지 않게 한다. 다만 미래 모드를 지금 모두 구현하지 않는다.

## 10. 에셋 계약 — 외부 제작물을 넣는 방식

별첨 이미지 제작 프롬프트와 오디오 제작 프롬프트를 읽고, 정확히 일치하는 ID를 manifest에 등록한다. ID는 고정하고 실제 파일 URL은 변경 가능하게 한다. 이미지 prompt로 만든 스프라이트 시트의 정렬이 정확하다고 가정하지 않는다. 단일 이미지로 받으면 빌드 도구가 trim·pivot 보존·atlas pack을 수행한다.

이미지 manifest에는 id, kind, url, dimensions, pivot, hardpoints, footprint, variant, license/source, version, optionalFallback을 둔다. 실제 게임 충돌 도형은 별도 physicsSpec에 두고 알파 채널에서 자동 추출한 윤곽을 무검증 사용하지 않는다.

오디오 manifest에는 id, bus, url, gain, loopStart/End, variants, concurrencyLimit, cooldownMs, priority를 둔다. BGM/SFX/UI 각각 음량과 음소거, 음향 미리듣기를 제공한다. 첫 사용자 제스처 후 오디오를 활성화한다. 중복 재생이나 탭 복귀 시 음악 겹침이 없어야 한다.

외부 에셋이 아직 없어도 그레이박스로 규칙과 네트워크 개발은 계속하되 개발 화면임을 표시한다. 최종 미술을 기다린다는 이유로 기능을 중단하지 않는다. 대신 최종 에셋 부재 항목을 asset-audit 리포트로 제출하고 “시각 완성 승인 전” 상태를 표시한다. 첫 경기의 대표 화면은 실제 공급 에셋으로 반드시 다시 검수한다.

큰 이미지는 원본을 그대로 초기 로드하지 않는다. 장면별 로딩과 다음 장면 preload, 1×/2× 해상도, texture atlas 및 적절한 압축을 사용한다. 최소 로비 자원과 첫 경기 자원을 구분한다. 첫 화면 필수 전송량 목표 3MB 이하, 첫 경기 필요 자원 목표 8MB 이하로 시작해 실제 품질과 측정에 따라 조절한다. 긴 WAV 원본은 배포하지 않고 웹용 압축본으로 제공한다.

## 11. 검증 목표와 완료 조건

다음 수치는 구현 전 보장값이 아니라 출시 판단에 사용할 목표다. 장치·지역·회선·플랜·에셋 상태를 함께 기록한다.

### 필수 시나리오

1. 교사가 클래스 생성 → 학생 30명 입장 → 학생 6명을 방장 지정 → 방장이 각 방에 자동 참여 → 나머지 학생 배정.
2. 기본 6개 방에 5명씩 참가한 상태에서 교사가 한 방 여섯 번째 자리에 참가하고 다른 방으로 관전 전환. 이전 자리가 정확히 반환됨.
3. 방별 봇 추가·제거·난도 변경, 봇 전용 시험 방, 솔로 봇 5대와 전체 대회.
4. 6번째 자리 동시 입장 요청, 여러 탭, 중복 명령, 재접속, 방 이동에도 정원과 단일 자리 보장.
5. 학생의 교사 명령 위조, 방장의 클래스 제어, 다른 클래스 방 접속, 상대 명령 조회 요청을 서버에서 거부. 사용자에게는 한국어 오류를 보여준다.
6. 네트워크 단절 10~60초, 방장 이탈, 교사 이탈, DO 휴면/재시작, 계산 도중 장애, alarm 중복에도 점수 중복 없이 복구.
7. 마감 때 미제출자는 미리 고지한 안전 명령. 전원이 같은 화면 단계와 같은 경기 결과를 봄.
8. 질량·마찰·자기력·범퍼·벽 관통·겹침·낙하·재진입·점수 판정 물리 테스트.
9. 규칙상 동일한 입력을 같은 엔진 버전에서 반복한 테스트, 리플레이 결과와 권위 상태 일치. 렌더링 프레임 수가 결과를 바꾸지 않음.
10. 최소 두 실제 브라우저/기기에서 연결해 한 방 경기 확인. 자동 봇 부하는 실제 브라우저 확인을 대체하지 않음.

### 성능/운영 테스트

- 목표 부하: 학생 30명 + 교사 1명, 6개 방 동시 진행, 봇으로 활성 로봇을 최대 36대까지 채운 시나리오. 로비와 방 이중 연결이 있다면 실제 소켓 수를 따로 보고한다.
- 20분 이상 실제 워크플로 부하: 조립, 제출, 전투, 피트스톱, 관전 이동, 일부 재접속 포함. 모두가 전투 중일 때도 시험.
- 100~200ms RTT와 작은 패킷 손실 조건에서 입력 ACK p95 300ms 이하, 전투 시작 시각 차 p95 150ms 이하를 목표로 한다. 완전 잠금 동기화를 강요해 느린 한 명이 전체를 멈추게 하지 않는다.
- 명령 확정→전투 시작 p95 1.5초 이하, 9초 물리 구간 계산 p95 250ms 이하 목표. 미달 결과를 숨기지 않는다.
- 실제 교실 노트북 목표 60fps, 저사양 품질 모드 30fps 이상. 30fps에서도 경기 결과 동일. 측정 장치와 최저/중간 프레임을 보고한다.
- 봇 계산·물리 계산 CPU, 메모리, WebSocket 전송량, 저장소 쓰기, 정적 자산 전송량, 비용 추정과 한계 기록.
- 방에 사람이 없을 때 유한한 봇 시험을 제외하고 지속 계산하지 않는다. 교사 자동 시험은 횟수/시간 제한 후 정지한다.
- 실제 배포 부하를 테스트하지 못했다면 “30인 운영 검증 완료”라고 쓰지 않는다. 로컬 결과와 운영 결과를 분리한다.

### 게임성과 화면 검수

- 초보자가 긴 설명 없이 첫 로봇을 장착하고 3개 명령을 제출할 수 있는지 관찰한다.
- 3종 프리셋과 각 주요 장치가 상대·지형에 따라 장단점을 가지는지 봇 결과와 사람이 확인한다. 봇 승률만으로 재미가 검증됐다고 하지 않는다.
- 실제 에셋 적용 상태에서 도시 입구, 격납고, 조립, 전술, 6대 전투, 피트스톱, 시상대, 교사 관제실 스크린샷을 확인한다.
- 텍스트 잘림, 로봇 겹침, 작은 클릭 영역, 색 의존, 명령 제출 여부 혼동, 배경과 판정 불일치, 음악 루프 단절을 수정한다.

## 12. 구현 순서와 최종 납품

1. 기존 저장소·지침·실행 환경 확인, README에 선택한 버전과 구조 기록. 새로운 저장소라면 독립 프로젝트로 시작한다.
2. 화면 흐름 및 game-core/physics/protocol 뼈대. 서버 엔진이 Cloudflare 런타임에서 실제 빌드·실행되는지 먼저 검증.
3. 한 경기장, 로봇 2대, 범퍼, 3슬롯 명령, 물리 충돌, 점수, 리플레이가 이어지는 플레이 가능한 세로 단면 완성.
4. 실제 DO/WebSocket으로 두 브라우저 연결, 서버 권위·재접속·단계 마감 검증.
5. 클래스/교사/방장/자리 분배/관전/봇 기능 완성.
6. 6대 전투와 세 챕터, 부품 선택·피트스톱·시상대, 솔로 전체 흐름 완성.
7. 외부 에셋 manifest 통합, 아트·오디오 QA, 접근성·저사양 옵션 적용.
8. 권한/복구/물리/부하 테스트, GitHub CI와 Cloudflare staging 배포 구성, 운영 문서 완성.

첫 단계에서 계획만 출력하고 작업을 종료하지 않는다. 저장소에서 구현 가능한 다음 단계로 계속 진행한다. 동시에 거대한 파일 한 개에 모든 기능을 몰아넣지 않는다. 실행 중 새 문제가 생기면 작은 수직 단면으로 해결한 뒤 전체에 적용한다.

최종 납품에는 소스, lockfile, lint/typecheck/test/build 명령, 환경변수 예제(비밀값 제외), Wrangler 구성과 migration, CI, 로컬/배포/교사 운영 안내, asset manifest와 누락 리포트, 물리·게임 균형 데이터, 성능·복구 테스트 결과, 실제 완료와 외부 대기 항목을 구분한 체크리스트를 포함한다.
